# Docs That Don't Rot

Install docs written once and validated on the author's machine start rotting the day they merge. This project's defense is structural: make docs drift break CI, keep platform docs separate, and never hand-write anything version-shaped.

## The procedure

1. **Per-OS docs, not one doc with tabs.** `docs/install/` splits macOS / Windows / Linux. Each carries its platform's real commands (Linux means `apt` AND `dnf` — "Linux" is several platforms), its platform's real error messages, and its own troubleshooting.
2. **Gate command blocks against the code that runs them.** Any fenced code block in `docs/install/*.md` tagged `<!-- validate -->` is checked by `scripts/validate-install-docs.py` (a CI gate): every line of the block must appear, after normalization, in `scripts/desktop-prod.sh`. Blocks that exist for human readability only are tagged `<!-- validate: skip -->`. When you change the install script, this gate forces the docs to follow in the same PR.
3. **Never hand-write version-pinned URLs or filenames** (`OmniVoice.Studio_0.2.7_aarch64.dmg`). They 404 after the next release. Templated/generated by the release workflow, or linked via `/releases/latest`.
4. **Date-stamp validation.** Install docs carry a "last validated: <date> on <OS versions>" line. A stale stamp is honest; a missing stamp is a lie by omission.
5. **Docs and in-app errors quote each other verbatim.** The error UI's remediation text and the doc's command must be word-for-word identical (see `skills/error-ux.md`); the docs deeplink map (`backend/core/error_docs_map.py`) is the join point — if you rename a docs anchor, grep the map.
6. **Security-sensitive workarounds get framed, not just pasted.** The `xattr -cr` Gatekeeper workaround is documented WITH the SHA-256 verification step first and scoped to the one app path — never `sudo`, never global Gatekeeper disable. Teaching users to paste quarantine-stripping commands from docs is a phishing surface; the checksum step is the mitigation.

## Rules I was following

- **The validator is deliberately a one-way check.** Every validated docs line must exist in the install script, but the script may contain extra steps the docs don't show (log dirs, cleanup). That asymmetry catches "docs claim a command the install path doesn't run" without forcing docs to mirror every script line — the failure mode that matters is the user typing something that doesn't work, not the docs being incomplete.
- **The validator itself is regression-tested** (importable `main(root)` entry point, exercised against tmp-path fixtures). A CI gate nobody trusts gets deleted; a tested gate survives.
- **Write for the reader who is already failing.** Install docs are read by someone mid-error. Lead with the working command; put explanation after. Include the exact error text they're seeing so search/ctrl-F lands them on the fix.
- **Document honestly when there's no good answer.** For networks where no PyPI mirror works, the docs say "use a VPN" rather than shipping a broken default. A doc that pretends is worse than a doc that admits.

## Worked example (the INST-06 docs-drift gate)

The failure this prevents: install docs say `bun run setup:api`, someone later renames the script, docs now instruct a command that errors on step 1, and the project learns about it from Discord. `scripts/validate-install-docs.py` extracts every `<!-- validate -->`-tagged block from `docs/install/*.md`, normalizes lines (strip `$ ` prompts, CRLF→LF, skip comments), and asserts each appears in `scripts/desktop-prod.sh` — exiting 1 with the offending file+line so the CI log leads the contributor straight to the fix. The marker system is the judgment call encoded: not every code block is a contract (some are illustrative), so authors declare which blocks are load-bearing, and only those are gated. To add a new install step: change the script, update the docs block, tag it `<!-- validate -->`, and CI holds them together forever after.

## Failure signs

- A command block in install docs with no validate marker decision (tagged neither way).
- A hardcoded version number or release filename in any doc.
- Docs and error-UI text for the same remediation drifting apart in wording.
- A "Linux" section with only `apt` commands.
